# Deployment

Both parts run on Render from one Blueprint, [`render.yaml`](../render.yaml).

| Service | Type | Notes |
|---|---|---|
| `murtuza-truck-routing-api` | Docker web service (free) | Django + gunicorn (2 workers), file cache in `/tmp`. It sleeps after 15 idle minutes, and the frontend pings `/api/health/` on load to wake it. |
| `murtuza-truck-routing` | Static site (free, CDN) | The Vite build. It never sleeps. `VITE_API_BASE_URL` points it at the API. |

## Environment variables (API service)

| Variable | Required | Value |
|---|---|---|
| `TOMTOM_API_KEY` | yes (secret) | TomTom developer key, for routing and geocoding |
| `WEATHERAPI_KEY` | recommended (secret) | WeatherAPI.com key. Without it, forecasts come from NWS alone (US only). |
| `WEATHER_PROVIDERS` | no | `weatherapi,nws` (the default) |
| `WEATHERAPI_DAYS` | no | Forecast days on your WeatherAPI plan: `3` on Free, `7` on Starter |
| `NWS_USER_AGENT` | no | Overrides the default identifying User-Agent sent to NWS |
| `DJANGO_SECRET_KEY` | yes | Generated by the Blueprint |
| `DEBUG` | yes | `false` |
| `ALLOWED_HOSTS` | yes | `.onrender.com` |
| `CORS_ALLOWED_ORIGINS` | yes | The frontend's URL |
| `CACHE_URL` | yes | `filecache:///tmp/planner-cache` (shared by the gunicorn workers) |
| `GEOCODER_ORDER` | no | `tomtom,photon` (Photon refuses connections from Render's network) |

Secrets are entered in the Render Dashboard; a Blueprint never stores their values.

## First-time setup

1. Open https://render.com/deploy?repo=https://github.com/murtuza777/spotter_labs_assessment and approve the Blueprint.
2. Paste `TOMTOM_API_KEY` and, optionally, `WEATHERAPI_KEY` when prompted.

The rest is preset: CORS, the API URL in the frontend build, and a generated secret key.

## Setting or changing a key later

1. Render Dashboard → **murtuza-truck-routing-api** → **Environment**.
2. Add or edit the variable (for example `WEATHERAPI_KEY`) and choose **Save, rebuild, and deploy** (or **Save and deploy**). If you choose **Save** only, the new value is used after the next deploy or restart.

## Deploying a new commit

This repo is linked to Render by its public URL, so pushes don't trigger deploys. Deploy with the [Render CLI](https://render.com/docs/cli):

```bash
render deploys create srv-db9p2s5g1s2s739hbdag --commit <sha> --wait --confirm   # API
render deploys create srv-db9p2s5g1s2s739hbda0 --commit <sha> --wait --confirm   # static site
```

Changes to Blueprint values (non-secret variables in `render.yaml`) need **Blueprints → Manual sync** in the Dashboard.

## Verifying a deploy

```bash
curl https://murtuza-truck-routing-api.onrender.com/api/health/
```

Then plan the Denver → Salt Lake City demo trip in the app and check:

- **Plan:** three routes and a recommendation.
- **Weather source:** checkpoint details say "Weather source: WeatherAPI.com" (or "National Weather Service" if no key is set), and the forecast timeline shows the matching credit.
- **API response:** `meta.weather.providers[0]` in `/api/plan/` shows the first provider with `"statuses": {"200": N}`.
- **Logs:** the service logs show `weather provider=weatherapi … statuses={'200': …}` with no `breaker open` warning.

## Keep warm during review (optional)

Set the repository variable `API_HEALTH_URL` to the health URL, and [keep-warm.yml](../.github/workflows/keep-warm.yml) pings it every 10 minutes. Free web services share 750 instance-hours a month per workspace, so turn it off after the review.

## Rollback

Redeploy the previous commit with the same `render deploys create … --commit <previous sha>` command.
